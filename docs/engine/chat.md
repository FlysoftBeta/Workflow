# Chat

The Engine adapts Codex App-Server and Claude Code to a shared conversation model. Android renders that model and submits `chat.command`; it never constructs an `AgentBackend` or a vendor process launcher. Rust remains the public Workspace RPC and persistence authority.

`:app:client` contains the retained immutable state, items, requests, events, catalogs, accounts, conversation-index value types, streaming text, pure `AgentReducer` and `rpc/ChatWire`; their Kotlin package identities remain stable for wire compatibility. The Engine side is the Rust `workflow-chat` crate in `engine/chat`, linked into Server: the model and in-place reducer, the bounded journal, the conversation index, the composer-revision send ledger, the optional-tool demand policy, the Codex App-Server and Claude Code adapters, and the `Chat` service facade that decodes `chat.command`. Server implements its ports and owns the chunked snapshot transfer; see [Server](server.md).

The crate depends only on Environment. Its ports are the guest runtime (`AgentRuntime`, which Server implements with the Environment runtime's piped spawn), guest agent-home reads, tool status and the optional Claude install, typed Chat documents, agent preferences in the revisioned configuration, and a Workspace bridge for attachments, composer acknowledgement and conversation removal. A source test keeps the crate free of direct filesystem, process and libc access. Vendor frames are parsed once into an exact-token JSON tree and read through tolerant typed projections, so a field of an unexpected type reads as absent, as the Kotlin accessors did; unknown methods, notifications, fields and server request IDs stay in named opaque values. Object members are re-encoded in canonical key order. Frame bodies and credentials are not logged.

## Rust port and device acceptance

The Rust implementation is the only chat path. The Kotlin `:engine-chat` service, the Engine-only `:agent` adapters, the service JAR, the bundled JRE and their packaging were deleted on 2026-10-04 by explicit user decision, before isolated API 28 guest Chat acceptance; git history is their archive. That acceptance, with zero skips against the integrated source, is still pending. Required device cases include snapshot/watch, unauthenticated Codex/account startup, reattachment, Claude install/initialization and generation restart. Real-account turns and physical ARM64 behavior remain separate acceptance work.

Host evidence covers the frozen Kotlin reducer and approval-card goldens, replay of the recorded Codex 0.157 and Claude 2.1.283 sessions through the actual Rust adapters (ported from `CodexBackendReplayTest`, `ClaudeBackendReplayTest`, `CodexLoginTest`, `CodexQueueTest`, `CodexEventsTest` and `ClaudeUnitTest`), the transport, ledger, journal, index and tool-policy cases, and command-level service tests. These do not replace device acceptance.

Recorded deviations from the Kotlin adapters: the advanced console forces the user reviewer on both settings methods; the send fingerprint covers the typed submitted composer, settings and mode, so a Kotlin-written record for the same revision fails explicitly rather than dispatching again; deleting a conversation removes its ledger records; prompts a Claude CLI re-arms in its `initialize` response are registered so the user's answer can reach it; and production unknown-request handling is the former `ASK_USER` policy (a card whose only choice rejects the request). Engine-authored Chinese strings are kept for parity.

The port preserves unknown traffic, original request IDs, explicit Codex user review, no automatic approval, send ambiguity and exact composer acknowledgement. A restart replaces the whole service, so the journal and every backend process get new epochs and stale cards cannot answer reused requests.

The cutover retains `ChatWire`. Replacing Android's event reducer with Engine-reduced projection changes is a later coordinated protocol/client change.

## From protocol frames to conversation state

An adapter converts wire frames into `AgentEvent` values and passes them to an `EventSink`. The Engine journal folds each event in place with the reducer under its lock. Its revisioned journal supplies snapshots and ordered event batches to the Android `AgentHub`, which is now an RPC client with a disposable reducer projection. Metadata includes conversation entries, measured backend availability, login methods, default permissions, and process epochs.

State separates backend-wide data, threads, and pending requests. Backend data includes process and account status, limits, available models, MCP state, notifications, and preserved unknown frames. Threads are keyed by `ThreadKey` and requests by `RequestKey`, retaining the distinction between backend and raw server request ID.

Codex uses its native thread, turn, and item IDs. Claude uses `session_id` for a thread, the client's prompt UUID for a turn (also used as `command_uuid` and `result.user_message_uuid`), `<message.id>:<block-index>` for text and thought items, and `tool_use.id` for tool items. The neutral item model represents user attachments, streaming assistant messages and their commentary/final phases, reasoning, plans, commands and output, file diffs, tool/MCP calls, nested agents, searches, images, markers, notices, and unknown JSON.

Incremental text appends by item ID through `StreamText`. A completion frame replaces content with its authoritative value, retaining already streamed content if the completion omits it. When a turn ends, unfinished items become `INCOMPLETE` and its pending requests become `EXPIRED`; their cards remain visible but cannot be answered. Unknown message phases are resolved at turn end with the last message treated as final. Process exit fails running turns for that backend and expires their requests. The reducer never answers requests.

The Engine adapter creates a queued turn before vendor submission. `TurnBound` or the backend's echoed user input associates it with the backend turn, regardless of arrival order. Echoes do not overwrite the user's attachment composition. Historical Codex turns are fetched using `thread/turns/list` with `itemsView:full`, paged newest first and arranged oldest first in the model. Claude history is read through an Engine-provided `ClaudeTranscriptSource` from the CLI's guest configuration directory. History merging retains a more complete live turn rather than replacing it with a poorer historical copy.

## Conversation identity and controls

The conversation index and `ConversationEntry` track the application's conversation ID, backend and backend thread ID, title, cwd, timestamps, archive state, fork source, last model/effort selection, and preview. The Engine service owns the index, persisted as the `chat`/`conversations` document through Environment's document store. Index refresh, search, and sorting are pure operations. Claude lacks backend listing and archival, so the Engine-owned index provides those features. Confirmed deletion removes that conversation's references from sessions and its composer draft without affecting unrelated resources.

The model/effort slider is derived from `ModelCatalog`, with model segments, supported reasoning levels, and defaults. A hidden model appears only while it is currently selected, and remembered selections are clamped to available values. Changes affect the next turn: Codex sends `model` and `effort` in `turn/start`; Claude applies `set_model` and `apply_flag_settings{effortLevel}` before sending.

Attachments refer to guest paths under `/workspace`. Codex uses `localImage` for images and path references in text for other files. Claude sends images as base64 `image`, PDFs as base64 `document`, and other files as `@path` for the CLI to read. Model input modalities control whether an attachment type is offered.

The common UI supports account flows, process health, interruption, approvals, user questions, elicitation, plans, model selection, attachments, reasoning, command output, diffs, tools, limits, and conversation history. Menus expose fork, compaction, queue control, and an explicit advanced console. MCP startup status has a dedicated view. Review mode, rollback, file suggestions, context-usage breakdown, and several advanced vendor features remain console operations rather than complete dedicated UI flows. Unknown capabilities remain available as preserved generic protocol data instead of disappearing from the model.

## Process launch and credentials

`AgentRuntime::spawn(SpawnSpec {argv,cwd,env,label})` is the Engine port returning piped stdio and a process with `wait`, `is_alive` and `kill`. Server implements it with the Environment runtime, so children run inside the verified environment with the guest workspace layout and are counted for restart. Android has neither this port nor the vendor adapters in its production dependency graph. An unavailable environment produces preparation or failure, never a host or demonstration backend. Stderr is diagnostic, and adapters retain a bounded 32 KiB tail without publishing secrets to logs.

The Engine payload binds Codex at `/opt/workflow/tools/codex/bin/codex`; it carries no Java runtime or chat service. Claude is an optional Engine job at `/opt/workflow/tools/claude/bin/claude`. Android requests installation by tool ID and renders measured status; paths, release selection, downloads and verification stay in Engine. See [environment](environment.md) for distribution and retry semantics.

Codex launches `/opt/workflow/tools/codex/bin/codex app-server`, using one process for multiple threads and its Engine-selected guest `CODEX_HOME`. Agent homes are workspace data: Codex uses `.workspace/agents/codex` and Claude `.workspace/agents/claude`, bound in the guest at `~/.codex` and `~/.claude` so chat and terminals share one login, while the tools themselves live in the read-only `.workspace/agents/tools/` bound at `/opt/workflow/tools`. Credential, session and history files stay hidden from the explorer. Its 0.157.1 binaries for arm64-v8a and x86_64 are pinned by SHA256 in `third_party/codex/manifest.json`. Codex owns credentials beneath its guest home and supports device-code, browser-callback, and API-key login flows. The [Codex login state machine](#codex-login-state-machine) defines how the adapter tracks an attempt.

Claude starts `claude -p` with `--input-format stream-json`, `--output-format stream-json`, `--verbose`, `--include-partial-messages`, `--replay-user-messages`, `--permission-prompt-tool stdio`, and an allowed `--permission-mode`. Optional model and effort parameters precede either a new session ID or resume/fork parameters. Each session has a process; an idle process warmed by `start()` becomes the next new session. Its Engine-selected guest directories are `CLAUDE_CONFIG_DIR`, `TMPDIR`, and `CLAUDE_CODE_TMPDIR`.

Both launchers filter inherited `OPENAI_*`, `CODEX_*`, `ANTHROPIC_*`, `CLAUDE_*`, `LD_PRELOAD`, and `LD_LIBRARY_PATH` variables. Claude additionally filters `CLAUDECODE` and disables its updater, telemetry, error reporting, and nonessential traffic through explicit variables. Credentials supplied deliberately by `ClaudeConfig` are separate from inherited host values. API keys remain in memory; persistent CLI login belongs to files in guest home. Claude login runs `claude auth login` or `claude setup-token` in a terminal. Refreshing Claude account state restarts an idle process to read new credentials.

## Codex login state machine

Codex reports a login through `account/login/start`, which returns `loginId` with a device code or authorization URL, and the `account/login/completed {loginId?, success, error?}` notification. `account/updated {authMode, planType}` follows a successful login, and `authMode: null` states that credentials are gone. `account/read {refreshToken:false}` returns `{account|null, requiresOpenaiAuth, workspaceRouting}`; `account/login/cancel {loginId}` answers `canceled` or `notFound` and is followed by a failed completion. The completion's `loginId` is nullable in the protocol.

The pinned 0.157.1 app-server was driven through complete logins against a local mock issuer, using its `CODEX_APP_SERVER_LOGIN_ISSUER` override and fabricated tokens, so no real account was involved. After the token exchange, Codex performs workspace-routing discovery against the ChatGPT backend before it reports completion. On success it then sends `account/login/completed` followed immediately by `account/updated`, and an `account/read` sent after the completion already returned the account. When discovery fails or exceeds its fifteen-second limit, Codex still stores the credentials and the browser still shows success, but the completion reports `success:false` with errors such as `workspace routing discovery timed out`; later `account/read` calls answer with that JSON-RPC error instead of `null`. Codex serves account requests one at a time, and each such read again waits up to fifteen seconds. In the measured run, a new `account/login/start` waited 46 seconds behind three queued reads. Thread and model requests were not delayed.

The adapter keeps one attempt and never holds its lock across a request:

| Phase | Entered by | Leaves when |
| --- | --- | --- |
| Starting | `login` emits `Progress(attemptId)` before sending `account/login/start` | The start answers with a flow (Waiting), an immediate completion such as an API key (finished), or an error (failed flow); Cancel ends it at once and the late start answer's login is cancelled on the server |
| Waiting | A device-code or browser flow | A matching completion arrives; any account read is authenticated; Cancel, process exit or the fifteen-minute deadline fails it and requests server cancellation |
| Confirming | A matching successful completion, emitted immediately so the account becomes signed in | An authenticated read fills in the account, or bounded reads after 0, 0.5, 1, 2 and 4 seconds end with a `loginAccountUnconfirmed` notice while the account stays signed in |

At most one `account/read` is outstanding. Polls, completion confirmations, resume re-checks and `refreshAccount` join it, and a caller that stops waiting after thirty seconds never sends another read. Polling starts at two seconds and doubles to at most fifteen seconds after a failure. A failed or unanswered read emits `AccountCheckFailed`; it is shown with the waiting flow and never ends the attempt. A completion for another login ID is ignored, while a successful or unattributed completion triggers an account read that can finish the current attempt. A completion that arrives before the start answer is processed is kept for that attempt. A failed matching completion ends the attempt with its error and then reads the account once, which shows either credentials Codex stored anyway or the read error. Starting failures are returned and emitted as a failed `Completed` flow rather than thrown. Startup read failures are also recorded instead of leaving the account silently unknown.

`AccountState.checkError` and the `AccountCheckFailed` event are the only wire additions. The reducer applies these rules, in order, to every answered account read:

1. An authenticated read replaces the account and ends any login flow.
2. While the flow is a successful completion, an unauthenticated read changes nothing. A null or lagging read therefore never overrides a confirmed completion.
3. While an attempt is pending (device code, browser, or `Progress` with an attempt ID and no error), a logged-out read keeps `LOGGING_IN` and the flow.
4. Otherwise the read replaces the account and keeps a failure or terminal flow visible.

Any answered read clears `checkError`, and so does a new pending flow. A process start drops a successful completion flow so the new process's read applies. The adapter emits `LoginChanged(null)` before reading when `account/updated` carries `authMode: null` and no attempt is running, so a sign-out elsewhere is shown. The pure `LoginView` projection in `:app:client` maps the account to the Checking, SignedIn, Idle, Starting, Waiting or Terminal phase used by the UI. Its resume policy re-reads the account after 0, 2 and 5 seconds while not signed in.

Unit tests replay these orders through the adapter: completion before or after the poll, null reads after completion, an unattributed completion, a routing failure with erroring reads, held reads with resume re-checks and cancellation, cancellation while starting, start failure, sign-out and startup read failure. A real ChatGPT account, the tablet's network path and the Android lifecycle under a real browser remain unverified by automation.

## Submission and reconnect semantics

`send` carries a client operation ID, turn settings, message parts, and the exact submitted composer draft including revision. Before vendor dispatch, the service commits an intent and argument digest through its send ledger. A repeated accepted operation returns the existing result and can finish acknowledgement; an argument mismatch or an unresolved outcome fails explicitly. An ambiguous vendor submission is never automatically replayed. Only backend acceptance permits acknowledgement of the exact submitted composer, preserving later edits.

The chat service has a fresh epoch for each lifetime; every backend process start also changes its process epoch. Watches with an expired journal cursor or different service epoch request a fresh snapshot. Approval responses include the process epoch captured with the displayed request, so a reused vendor request ID cannot authorize a new process's request. The embedded Server and service stop when their transport closes. Reconnect rehydrates committed metadata and vendor history; it does not preserve a live process across Server shutdown.

## Approval and protocol fidelity

Approval requests are never automatically approved. Only a user's card action invokes the adapter's response path. Factual host capability requests such as `currentTime/read` can receive facts, and unsupported dynamic tool calls can receive `success:false`; neither is a grant of permission.

Every relevant Codex thread/turn request explicitly sends `approvalsReviewer:"user"`, including requests issued through the advanced console. If the server reports a different reviewer, the adapter blocks sending for that thread. Available decisions are mapped from the server's exact set. In the absence of a supplied set, only one-time accept, reject, and cancel choices are offered; session and persistent grants are labelled separately. Claude follows its permission suggestions, removes persistent choices when `suppress_always_allow_rule` requires it, and does not provide one-click approval when user interaction is required.

Requests traveling in the two JSON-RPC directions use separate maps. Server request IDs preserve their original string or integer form on the response. Unknown methods, notifications, and fields remain JSON values represented by `UnknownRecord` or `UnknownItem`. Unknown server requests default to an explicit protocol error, with an optional generic-card policy; they cannot be treated as successfully approved work. Claude control responses are accepted only for a currently awaited `request_id`, so echoes cannot complete unrelated requests. Undeclared `request_user_dialog` requests are not answered.

Claude's permitted modes are `default`, `acceptEdits`, `plan`, and `dontAsk`. `bypassPermissions`, `auto`, and `--dangerously-skip-permissions` are rejected, including through extra arguments. The application never manufactures an approval response to a vendor request. Secrets and identifying account values do not belong in logs, source fixtures, or evidence bundles.

## Protocol assets and verification

The Codex App-Server schema bundle, the Claude control inventory, their regeneration scripts and the generated coverage golden belonged to the deleted Kotlin `:agent` module and were removed with it. The Rust adapters type the frames they consume and keep everything else as named opaque values; a Rust inventory and coverage check is not yet in place.

Besides mapping frames to neutral events, an adapter may answer a vendor request with a fact or a negative capability result, reject it with a protocol error, deliberately leave it unanswered, show it as a card for the user, or retain it for the explicit console. An automatic answer never means approval.

The Rust suite is `cargo test --manifest-path engine/Cargo.toml --locked -p workflow-chat`; its `testing` feature provides in-memory pipes, a fake guest runtime, a reducing event store and the ported `ScriptedServer`, replaying the redacted fixtures in `engine/chat/tests/fixtures/`. `tools/workflow check chat` runs it through the suite catalog, and `tools/workflow check client` runs the `:app:client` codec/model tests. Together they cover wire round trips, bounded journal snapshots, stale epochs, send deduplication, index concurrency and vendor adapter replay. `codex_replay` and `claude_replay` drive the actual adapters through `ScriptedServer` fixtures, covering such paths as approvals, interruption, hooks, model changes, forks, and unauthenticated startup. None of this constitutes Android account acceptance.

Historical integration checks exercised real backend startup before the Engine service separation. They do not validate the in-process Rust chat path. They did not establish successful real-account model turns for both backends on a device. User input, elicitation, steer, nested-agent, and incremental command-output cases include synthetic unit coverage without captured live evidence. Codex queue synchronization uses pagination and backend submission IDs, and guards against a late queue snapshot moving an already running turn backwards. Native rendering evidence is in the [chat report](../archive/implementation-1.0.0/reports/rewrite/native-chat.md); account and device limits remain in [status](../status.md).

Send identity is anchored to the persisted conversation ID and composer revision. Client operation UUIDs are correlation values, so recreating a client cannot bypass a pending or accepted submission record. Repeated saves of unchanged input retain that revision.
