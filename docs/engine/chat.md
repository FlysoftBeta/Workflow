# Chat

The Engine adapts Codex App-Server and Claude Code to a shared conversation model. Android renders that model and submits `chat.command`; it never constructs an `AgentBackend` or a vendor process launcher. Rust remains the public Workspace RPC and persistence authority.

`:app:client` contains the retained immutable state, items, requests, events, catalogs, accounts, conversation-index value types, streaming text, pure `AgentReducer` and `rpc/ChatWire`. Their Kotlin package identities remain stable for wire compatibility. The temporary Engine-only `:agent` module depends on these definitions and supplies `AgentBackend`, `AgentStateStore`, thread options, process ports, JSONL transports, and the `codex/` and `claude/` implementations. Protocol resources under `agent/src/main/resources/protocol/` are pinned to Codex CLI 0.157.1 and the Claude Agent SDK 0.3.283 inventory. `:engine-chat` owns the service, hub, index writer, event journal and send ledger. Its fat JAR runs on the guest Linux JRE supplied by the Engine tools distribution.

Rust's `chat.rs` supervises that service over private bidirectional JSON-RPC stdio. Requests to `chat.snapshot`, `chat.watch` and `chat.command` are forwarded; allowlisted callbacks provide workspace commands, files and `chat` documents. Callback request IDs have a separate direction and are handled without retaining the workspace mutex while the service waits. Recursive chat/process callbacks are rejected. Private workspace directories remain masked in the guest: the service persists through callbacks, not a writable private-state mount. Frame bodies and credentials are not logged.

## Rust port and cutover gate

The decided owner is the Rust `workflow-chat` crate in `engine/chat`. The current Rust work provides a partial typed domain, policies and ports; it does not replace the production Kotlin adapters or guest service. Agent/backend defaults belong to Chat even while the transport preserves the existing configuration shape. Rust Chat depends on Environment and uses Server-implemented ports for cross-domain composer, file and conversation effects. It must not perform ordinary workspace IO or spawn vendor processes directly.

The Kotlin service, `:agent` implementation, JAR, JRE payload and current client event reducer remain until the coordinated cutover is proven. Removal requires reducer and codec goldens, adapter outgoing-frame/state replay parity, service journal/index/ledger parity, and zero-skip isolated API 28 guest Chat acceptance against the integrated source. Required device cases include snapshot/watch, unauthenticated Codex/account startup, reattachment, Claude install/initialization and generation restart. Real-account turns and physical ARM64 behavior remain separate acceptance work.

The port must preserve unknown traffic, original request IDs, explicit Codex user review, no automatic approval, send ambiguity and exact composer acknowledgement. Raw-console reviewer enforcement must also cover both vendor settings methods. Restart must rotate service/journal and backend process identities so stale cards cannot answer reused requests. Partial policy tests are useful evidence for those policies, never proof of complete adapter parity.

The first accepted Rust cutover retains `ChatWire`. Replacing Android's event reducer with Engine-reduced projection changes is a later coordinated protocol/client change. The sections below describe the retained production behavior that the port must match.

## From protocol frames to conversation state

An adapter converts wire frames into `AgentEvent` values and passes them to an `AgentEventSink`. `AgentStateStore` synchronously folds events with `AgentReducer.reduce` and publishes immutable `AgentState` through `StateFlow`. The Engine chat hub owns that store. Its revisioned journal supplies snapshots and ordered event batches to the Android `AgentHub`, which is now an RPC client with a disposable reducer projection. Metadata includes conversation entries, measured backend availability, login methods, default permissions, and process epochs.

State separates backend-wide data, threads, and pending requests. Backend data includes process and account status, limits, available models, MCP state, notifications, and preserved unknown frames. Threads are keyed by `ThreadKey` and requests by `RequestKey`, retaining the distinction between backend and raw server request ID.

Codex uses its native thread, turn, and item IDs. Claude uses `session_id` for a thread, the client's prompt UUID for a turn (also used as `command_uuid` and `result.user_message_uuid`), `<message.id>:<block-index>` for text and thought items, and `tool_use.id` for tool items. The neutral item model represents user attachments, streaming assistant messages and their commentary/final phases, reasoning, plans, commands and output, file diffs, tool/MCP calls, nested agents, searches, images, markers, notices, and unknown JSON.

Incremental text appends by item ID through `StreamText`. A completion frame replaces content with its authoritative value, retaining already streamed content if the completion omits it. When a turn ends, unfinished items become `INCOMPLETE` and its pending requests become `EXPIRED`; their cards remain visible but cannot be answered. Unknown message phases are resolved at turn end with the last message treated as final. Process exit fails running turns for that backend and expires their requests. The reducer never answers requests.

The Engine adapter creates a queued turn before vendor submission. `TurnBound` or the backend's echoed user input associates it with the backend turn, regardless of arrival order. Echoes do not overwrite the user's attachment composition. Historical Codex turns are fetched using `thread/turns/list` with `itemsView:full`, paged newest first and arranged oldest first in the model. Claude history is read through an Engine-provided `ClaudeTranscriptSource` from the CLI's guest configuration directory. History merging retains a more complete live turn rather than replacing it with a poorer historical copy.

## Conversation identity and controls

`ConversationIndex` and `ConversationEntry` track the application's conversation ID, backend and backend thread ID, title, cwd, timestamps, archive state, fork source, last model/effort selection, and preview. The Engine service owns `ConversationIndexFile`, with persistence routed through Rust opaque-document callbacks. Index refresh, search, and sorting are pure operations. Claude lacks backend listing and archival, so the Engine-owned index provides those features. Confirmed deletion removes that conversation's references from sessions and its composer draft without affecting unrelated resources.

The model/effort slider is derived from `ModelCatalog`, with model segments, supported reasoning levels, and defaults. A hidden model appears only while it is currently selected, and remembered selections are clamped to available values. Changes affect the next turn: Codex sends `model` and `effort` in `turn/start`; Claude applies `set_model` and `apply_flag_settings{effortLevel}` before sending.

Attachments refer to guest paths under `/workspace`. Codex uses `localImage` for images and path references in text for other files. Claude sends images as base64 `image`, PDFs as base64 `document`, and other files as `@path` for the CLI to read. Model input modalities control whether an attachment type is offered.

The common UI supports account flows, process health, interruption, approvals, user questions, elicitation, plans, model selection, attachments, reasoning, command output, diffs, tools, limits, and conversation history. Menus expose fork, compaction, queue control, and an explicit advanced console. MCP startup status has a dedicated view. Review mode, rollback, file suggestions, context-usage breakdown, and several advanced vendor features remain console operations rather than complete dedicated UI flows. Unknown capabilities remain available as preserved generic protocol data instead of disappearing from the model.

## Process launch and credentials

`ProcessLauncher.launch(LaunchSpec(argv,env,cwd,label))` is an Engine implementation port returning byte streams, `awaitExit`, and `kill`. The guest JVM uses it to launch children inside its verified environment. Android has neither this port nor the vendor module in its production dependency graph. An unavailable environment produces preparation or failure, never a host or demonstration backend. Stderr is diagnostic, and adapters retain a bounded 32 KiB tail without publishing secrets to logs.

The Engine payload binds Codex at `/opt/workflow/tools/codex/bin/codex`, Java at `/opt/workflow/tools/jre/bin/java`, and the service at `/opt/workflow/tools/chat/workflow-chat.jar`. Claude is an optional Engine job at `/opt/workflow/tools/claude/bin/claude`. Android requests installation by tool ID and renders measured status; paths, release selection, downloads and verification stay in Engine. See [environment](environment.md) for distribution and retry semantics.

Codex launches `/opt/workflow/tools/codex/bin/codex app-server`, using one process for multiple threads and its Engine-selected guest `CODEX_HOME`. Its 0.157.1 binaries for arm64-v8a and x86_64 are pinned by SHA256 in `third_party/codex/manifest.json`. Codex owns credentials beneath its guest home and supports device-code, browser-callback, and API-key login flows. While an asynchronous login is pending, the adapter checks account state every two seconds to recover a missing completion notification. A fifteen-minute deadline ends the wait and requests cancellation; cancellation and process exit also end waiting. Completion notifications are matched to the pending login ID, and failed login messages remain visible until a new attempt or authenticated account refresh.

Claude starts `claude -p` with `--input-format stream-json`, `--output-format stream-json`, `--verbose`, `--include-partial-messages`, `--replay-user-messages`, `--permission-prompt-tool stdio`, and an allowed `--permission-mode`. Optional model and effort parameters precede either a new session ID or resume/fork parameters. Each session has a process; an idle process warmed by `start()` becomes the next new session. Its Engine-selected guest directories are `CLAUDE_CONFIG_DIR`, `TMPDIR`, and `CLAUDE_CODE_TMPDIR`.

Both launchers filter inherited `OPENAI_*`, `CODEX_*`, `ANTHROPIC_*`, `CLAUDE_*`, `LD_PRELOAD`, and `LD_LIBRARY_PATH` variables. Claude additionally filters `CLAUDECODE` and disables its updater, telemetry, error reporting, and nonessential traffic through explicit variables. Credentials supplied deliberately by `ClaudeConfig` are separate from inherited host values. API keys remain in memory; persistent CLI login belongs to files in guest home. Claude login runs `claude auth login` or `claude setup-token` in a terminal. Refreshing Claude account state restarts an idle process to read new credentials.

## Submission and reconnect semantics

`send` carries a client operation ID, turn settings, message parts, and the exact submitted composer draft including revision. Before vendor dispatch, the service commits an intent and argument digest through its send ledger. A repeated accepted operation returns the existing result and can finish acknowledgement; an argument mismatch or an unresolved outcome fails explicitly. An ambiguous vendor submission is never automatically replayed. Only backend acceptance permits acknowledgement of the exact submitted composer, preserving later edits.

The chat service has a fresh epoch for each lifetime; every backend process start also changes its process epoch. Watches with an expired journal cursor or different service epoch request a fresh snapshot. Approval responses include the process epoch captured with the displayed request, so a reused vendor request ID cannot authorize a new process's request. The embedded Server and service stop when their transport closes. Reconnect rehydrates committed metadata and vendor history; it does not preserve a live process across Server shutdown.

## Approval and protocol fidelity

Approval requests are never automatically approved. Only a user's card action invokes the adapter's response path. Factual host capability requests such as `currentTime/read` can receive facts, and unsupported dynamic tool calls can receive `success:false`; neither is a grant of permission.

Every relevant Codex thread/turn request explicitly sends `approvalsReviewer:"user"`, including requests issued through the advanced console. If the server reports a different reviewer, the adapter blocks sending for that thread. Available decisions are mapped from the server's exact set. In the absence of a supplied set, only one-time accept, reject, and cancel choices are offered; session and persistent grants are labelled separately. Claude follows its permission suggestions, removes persistent choices when `suppress_always_allow_rule` requires it, and does not provide one-click approval when user interaction is required.

Requests traveling in the two JSON-RPC directions use separate maps. Server request IDs preserve their original string or integer form on the response. Unknown methods, notifications, and fields remain JSON values represented by `UnknownRecord` or `UnknownItem`. Unknown server requests default to an explicit protocol error, with an optional generic-card policy; they cannot be treated as successfully approved work. Claude control responses are accepted only for a currently awaited `request_id`, so echoes cannot complete unrelated requests. Undeclared `request_user_dialog` requests are not answered.

Claude's permitted modes are `default`, `acceptEdits`, `plan`, and `dontAsk`. `bypassPermissions`, `auto`, and `--dangerously-skip-permissions` are rejected, including through extra arguments. The application never manufactures an approval response to a vendor request. Secrets and identifying account values do not belong in logs, source fixtures, or evidence bundles.

## Protocol assets and verification

`CODEX=<binary> tools/update-protocol.py` regenerates Codex schemas, inventory, and Kotlin constants; generated TypeScript goes into ignored `artifacts/agent/`. `--kotlin-only` regenerates constants from the checked-in inventory. `tools/update-claude-protocol.py <claude-agent-sdk/package>` updates the Claude inventory. `ProtocolCoverageTest` checks inventory consistency and the generated [coverage document](../../agent/protocol-coverage.md), which can be updated with `tools/with-build-lock.sh ./gradlew :agent:test -Pagent.updateGolden=true`.

Coverage labels explain handling, not product acceptance: `model` maps neutral events, `adapter` sends commands, `transport` consumes protocol mechanics, `card` asks the user, `auto` answers facts or negative capability results, `reject` returns a protocol error, `never-answer` intentionally leaves a request unanswered, and `generic` retains it for the explicit console. In particular, `auto` must never mean approval.

While the JVM implementation remains, `tools/workflow check agent` runs the relevant `:app:client` codec/model tests, `:agent:test`, `:engine-chat:test` and `:engine-chat:serviceJar` through the suite catalog. It covers wire round trips, bounded journal snapshots, stale epochs, send deduplication, index concurrency and vendor adapter replay. `CodexBackendReplayTest` and `ClaudeBackendReplayTest` drive actual adapters through `ScriptedServer` fixtures, covering such paths as approvals, interruption, hooks, model changes, forks, and unauthenticated startup. Separate smoke tasks can exercise a real Codex process or a Claude mock API; they are not part of the ordinary unit suite and do not constitute Android account acceptance.

Historical integration checks exercised real backend startup before the Engine service separation. They do not validate the new guest JRE/service path. They did not establish successful real-account model turns for both backends on a device. User input, elicitation, steer, nested-agent, and incremental command-output cases include synthetic unit coverage without captured live evidence. Codex queue synchronization uses pagination and backend submission IDs, and guards against a late queue snapshot moving an already running turn backwards. Native rendering evidence is in the [chat report](../archive/implementation-1.0.0/reports/rewrite/native-chat.md); account and device limits remain in [status](../status.md).

Send identity is anchored to the persisted conversation ID and composer revision. Client operation UUIDs are correlation values, so recreating a client cannot bypass a pending or accepted submission record. Repeated saves of unchanged input retain that revision.
