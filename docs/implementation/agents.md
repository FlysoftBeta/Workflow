# Coding-agent adapters

The pure JVM `:agent` module adapts Codex App-Server and Claude Code to a common conversation model. It owns vendor transports, event mapping, request preservation, and approval constraints. The Android UI reads the resulting state and sends commands through the backend interface. Workspace persistence remains in the Engine: an adapter's in-memory protocol state is not a second workspace repository.

`AgentBackend.kt` defines the backend interface, `AgentStateStore`, thread options, and send modes. `model/` contains immutable state, items, requests, events, the reducer, catalogs, accounts, conversation-index types, and streaming text. `process/` defines the process-launch port. `transport/` handles JSONL framing, Codex JSON-RPC, and Claude stream-json control messages. `codex/` and `claude/` contain their corresponding launch parameters, mapping, and backend implementations. Protocol resources under `agent/src/main/resources/protocol/` are pinned to Codex CLI 0.157.1 and the Claude Agent SDK 0.3.283 inventory.

## From protocol frames to conversation state

An adapter converts wire frames into `AgentEvent` values and passes them to an `AgentEventSink`. `AgentStateStore` synchronously folds events with `AgentReducer.reduce` and publishes immutable `AgentState` through `StateFlow`. The process-level Android `AgentHub` owns a store; views observe it and invoke `AgentBackend` for actions.

State separates backend-wide data, threads, and pending requests. Backend data includes process and account status, limits, available models, MCP state, notifications, and preserved unknown frames. Threads are keyed by `ThreadKey` and requests by `RequestKey`, retaining the distinction between backend and raw server request ID.

Codex uses its native thread, turn, and item IDs. Claude uses `session_id` for a thread, the client's prompt UUID for a turn (also used as `command_uuid` and `result.user_message_uuid`), `<message.id>:<block-index>` for text and thought items, and `tool_use.id` for tool items. The neutral item model represents user attachments, streaming assistant messages and their commentary/final phases, reasoning, plans, commands and output, file diffs, tool/MCP calls, nested agents, searches, images, markers, notices, and unknown JSON.

Incremental text appends by item ID through `StreamText`. A completion frame replaces content with its authoritative value, retaining already streamed content if the completion omits it. When a turn ends, unfinished items become `INCOMPLETE` and its pending requests become `EXPIRED`; their cards remain visible but cannot be answered. Unknown message phases are resolved at turn end with the last message treated as final. Process exit fails running turns for that backend and expires their requests. The reducer never answers requests.

Sending creates a local queued turn first. `TurnBound` or the backend's echoed user input associates it with the backend turn, regardless of arrival order. Echoes do not overwrite the user's attachment composition. Historical Codex turns are fetched using `thread/turns/list` with `itemsView:full`, paged newest first and arranged oldest first in the model. Claude history is read through an application-provided `ClaudeTranscriptSource` from the CLI's guest configuration directory. History merging retains a more complete live turn rather than replacing it with a poorer historical copy.

## Conversation identity and controls

`ConversationIndex` and `ConversationEntry` track the application's conversation ID, backend and backend thread ID, title, cwd, timestamps, archive state, fork source, last model/effort selection, and preview. `ConversationIndexFile` supplies a typed view, with all persistence routed through Engine opaque documents. Index refresh, search, and sorting are pure operations. Claude lacks backend listing and archival, so the application index provides those features. Confirmed deletion removes that conversation's references from sessions and its composer draft without affecting unrelated resources.

The model/effort slider is derived from `ModelCatalog`, with model segments, supported reasoning levels, and defaults. A hidden model appears only while it is currently selected, and remembered selections are clamped to available values. Changes affect the next turn: Codex sends `model` and `effort` in `turn/start`; Claude applies `set_model` and `apply_flag_settings{effortLevel}` before sending.

Attachments refer to guest paths under `/workspace`. Codex uses `localImage` for images and path references in text for other files. Claude sends images as base64 `image`, PDFs as base64 `document`, and other files as `@path` for the CLI to read. Model input modalities control whether an attachment type is offered.

The common UI supports account flows, process health, interruption, approvals, user questions, elicitation, plans, model selection, attachments, reasoning, command output, diffs, tools, limits, and conversation history. Menus expose fork, compaction, queue control, and an explicit advanced console. MCP startup status has a dedicated view. Review mode, rollback, file suggestions, context-usage breakdown, and several advanced vendor features remain console operations rather than complete dedicated UI flows. Unknown capabilities remain available as preserved generic protocol data instead of disappearing from the model.

## Process launch and credentials

`ProcessLauncher.launch(LaunchSpec(argv,env,cwd,label))` returns an `AgentProcess` with byte-stream stdin/stdout/stderr, `awaitExit`, and `kill`. The production `EngineProcessLauncher` uses the Engine process API inside the customized environment. An unavailable environment produces a wait or explicit failure, never a host or demonstration backend. The launch specification provides the child environment without inheriting host credentials. Both backends carry their protocol on stdio; stderr is diagnostic, with a retained tail of 32 KiB.

Codex launches `/opt/workflow/bundled/libcodex.so app-server`, using one process for multiple threads and its application-owned `CODEX_HOME`. Its 0.157.1 binaries for arm64-v8a and x86_64 are pinned by SHA256 in `third_party/codex/manifest.json`. Codex owns credentials beneath its guest home and supports device-code, browser-callback, and API-key login flows. While an asynchronous login is pending, the adapter checks account state every two seconds to recover a missing completion notification. A fifteen-minute deadline ends the wait and requests cancellation; cancellation and process exit also end waiting. Completion notifications are matched to the pending login ID, and failed login messages remain visible until a new attempt or authenticated account refresh.

Claude starts `claude -p` with `--input-format stream-json`, `--output-format stream-json`, `--verbose`, `--include-partial-messages`, `--replay-user-messages`, `--permission-prompt-tool stdio`, and an allowed `--permission-mode`. Optional model and effort parameters precede either a new session ID or resume/fork parameters. Each session has a process; an idle process warmed by `start()` becomes the next new session. Its application-owned directories are `CLAUDE_CONFIG_DIR`, `TMPDIR`, and `CLAUDE_CODE_TMPDIR`.

Both launchers filter inherited `OPENAI_*`, `CODEX_*`, `ANTHROPIC_*`, `CLAUDE_*`, `LD_PRELOAD`, and `LD_LIBRARY_PATH` variables. Claude additionally filters `CLAUDECODE` and disables its updater, telemetry, error reporting, and nonessential traffic through explicit variables. Credentials supplied deliberately by `ClaudeConfig` are separate from inherited host values. API keys remain in memory; persistent CLI login belongs to files in guest home. Claude login runs `claude auth login` or `claude setup-token` in a terminal. Refreshing Claude account state restarts an idle process to read new credentials.

## Approval and protocol fidelity

Approval requests are never automatically approved. Only a user's card action invokes the adapter's response path. Factual host capability requests such as `currentTime/read` can receive facts, and unsupported dynamic tool calls can receive `success:false`; neither is a grant of permission.

Every relevant Codex thread/turn request explicitly sends `approvalsReviewer:"user"`, including requests issued through the advanced console. If the server reports a different reviewer, the adapter blocks sending for that thread. Available decisions are mapped from the server's exact set. In the absence of a supplied set, only one-time accept, reject, and cancel choices are offered; session and persistent grants are labelled separately. Claude follows its permission suggestions, removes persistent choices when `suppress_always_allow_rule` requires it, and does not provide one-click approval when user interaction is required.

Requests traveling in the two JSON-RPC directions use separate maps. Server request IDs preserve their original string or integer form on the response. Unknown methods, notifications, and fields remain JSON values represented by `UnknownRecord` or `UnknownItem`. Unknown server requests default to an explicit protocol error, with an optional generic-card policy; they cannot be treated as successfully approved work. Claude control responses are accepted only for a currently awaited `request_id`, so echoes cannot complete unrelated requests. Undeclared `request_user_dialog` requests are not answered.

Claude's permitted modes are `default`, `acceptEdits`, `plan`, and `dontAsk`. `bypassPermissions`, `auto`, and `--dangerously-skip-permissions` are rejected, including through extra arguments. The application never manufactures an approval response to a vendor request. Secrets and identifying account values do not belong in logs, source fixtures, or evidence bundles.

## Protocol assets and verification

`CODEX=<binary> tools/update-protocol.py` regenerates Codex schemas, inventory, and Kotlin constants; generated TypeScript goes into ignored `artifacts/agent/`. `--kotlin-only` regenerates constants from the checked-in inventory. `tools/update-claude-protocol.py <claude-agent-sdk/package>` updates the Claude inventory. `ProtocolCoverageTest` checks inventory consistency and the generated [coverage document](../../agent/protocol-coverage.md), which can be updated with `flock artifacts/.gradle.lock ./gradlew :agent:test -Pagent.updateGolden=true`.

Coverage labels explain handling, not product acceptance: `model` maps neutral events, `adapter` sends commands, `transport` consumes protocol mechanics, `card` asks the user, `auto` answers facts or negative capability results, `reject` returns a protocol error, `never-answer` intentionally leaves a request unanswered, and `generic` retains it for the explicit console. In particular, `auto` must never mean approval.

`flock artifacts/.gradle.lock ./gradlew :agent:test` runs pure model, transport, and adapter tests. `CodexBackendReplayTest` and `ClaudeBackendReplayTest` drive actual adapters through `ScriptedServer` fixtures, covering such paths as approvals, interruption, hooks, model changes, forks, and unauthenticated startup. Separate smoke tasks can exercise a real Codex process or a Claude mock API; they are not part of the ordinary unit suite and do not constitute Android account acceptance.

Recorded integration checks exercised real backend startup inside the environment. They did not establish successful real-account model turns for both backends on a device. User input, elicitation, steer, nested-agent, and incremental command-output cases include synthetic unit coverage without captured live evidence. Codex queue synchronization uses pagination and backend submission IDs, and guards against a late queue snapshot moving an already running turn backwards. Native rendering evidence is in the [chat report](../archive/implementation-1.0.0/reports/rewrite/native-chat.md); account and device limits remain in [status](../status.md).
